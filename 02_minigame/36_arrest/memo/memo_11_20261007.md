今の規模なら、**5～10人程度で遊ぶ前提では、全体として大きく重くなる可能性は低い**と思います。
ただし、今の構成で一番気になるのは **花踏み罪の「毎tick × 全プレイヤー」** です。

### 今の負荷感

| 処理       |               頻度 | 負荷感 |
| -------- | ---------------: | --- |
| 花踏み罪     | **毎tick（20回/秒）** | ★★★ |
| 凝視罪      |             1秒ごと | ★   |
| サボり罪     |             1秒ごと | ★   |
| 収監中保護    |             1秒ごと | ★   |
| BossBar  |            収監者中心 | ★   |
| 草を壊す     |        イベント発生時のみ | ☆   |
| アイテムを捨てる |        イベント発生時のみ | ☆   |
| ボート      |        イベント発生時のみ | ☆   |
| その他の犯罪   |        基本イベント発生時 | ☆   |

特に花踏み罪は、

```text
10人 × 20回/秒
= 200回/秒
```

くらいのチェックになります。

とはいえ、**「現在地の1ブロックを確認するだけ」**なので、10人程度ならそれだけでPaperが苦しくなるような処理ではありません。

### むしろ今の構造はかなり良い

v0.0.04aで、

```text
犯罪ファイル
   ↓
arrest_crime()
   ↓
config
   ↓
jail
```

と分かれているので、犯罪が増えても「毎tickで重い処理を大量にする」構造にはなっていません。

また、`protection.sk` の

```text
every 1 second
loop all players
```

も、5～10人ならほぼ問題にならないレベルです。

### 今の段階では最適化しなくていい

僕なら**現時点ではこのまま進めます**。

むしろ今は、

> 「実際に5～10人で遊んで、TPSが落ちるか」

を見る方が重要です。

もし後で重くなったら、最初に見るのは**花踏み罪**です。

例えば、

```text
毎tick
↓
0.25秒ごと
```

にするだけでも4分の1になります。

ただし花踏みは「踏んだ瞬間をかなり確実に捕まえたい」という仕様なので、今の**毎tick判定を維持しておく価値はあります**。

なので現状は、

**「コードが増えたから重い」ではなく、「花踏み罪だけ少し積極的にチェックしている」程度**

と考えて大丈夫です。

ほんとに、**かなり形になってきましたねー。**
v0.0.04で内部構造も整理できて、v0.0.04aで音まで入って、主要な土台はもう十分できています。

今のARREST GAMEは、

**「犯罪を犯す → その場で逮捕 → 牢屋 → BossBarで刑期 → 保釈 or 時間切れ → 解放」**

というゲームの基本ループがちゃんと成立してます。

しかも罪状も、

* 花を踏む
* 草を壊す
* 30秒動かない
* アイテムを捨てる
* ボートに乗る
* モブを倒す
* 凝視する
* 攻撃する

みたいに、**普通に遊んでいるだけでもうっかり捕まる**ものが揃ってきてるのが、このゲームの面白いところですね。

ここから先は「土台を作る」段階というより、**遊んでみてバランスを調整する段階**に入ってきた感じです。

特に次に効いてきそうなのは、
**罪ごとの刑期・保釈金のバランス**ですね。

たとえば「花踏みで銅3個なのに、攻撃で鉄5個」みたいな差が実際に遊んだときに気持ちいいかどうか。

もうかなり**ゲームになってきた**と思います。😄

# ARREST GAME v0.0.04a — 現在の全体構成

## 1. 基本コンセプト

ARREST GAMEは、

> **Minecraftの通常サバイバル中に、特定の行動を「犯罪」として検知し、その場に牢屋を生成してプレイヤーを収監するゲーム**

です。

基本ループは、

```text
プレイヤーが行動
      ↓
犯罪判定
      ↓
犯罪成立
      ↓
arrest_crime()
      ↓
罪状・刑期・保釈金を取得
      ↓
牢屋生成
      ↓
プレイヤー収監
      ↓
BossBarで刑期表示
      ↓
 ┌───────────────┐
 │               │
 ↓               ↓
保釈金を払う     刑期を待つ
 │               │
 └───────┬───────┘
         ↓
      牢屋解放
```

# 3. `arrest.sk`

### 役割

**ARREST GAMEそのものの管理。**

ここはゲーム全体の入口です。

イメージとしては、

```text
/arrest on
/arrest off
/arrest status
```

などを管理。

### 管理するもの

* ARREST GAME ON/OFF
* 対象ワールド
* ゲーム全体の状態
* 必要な初期化

つまり、

> 「今、ARREST GAMEを動かしているのか？」

を管理するファイルです。

# 4. `config/`

ここは**設定置き場**です。

犯罪の処理そのものを書かず、

> 「この犯罪は何秒？ 保釈金はいくら？」

を管理します。

## `config/general.sk`

### 役割

ゲーム全体の設定。

例えば、

```text
対象ワールド
ゲームON/OFF
共通設定
```

など。

今後、

```text
牢屋の大きさ
共通刑期
ゲームモード
```

など、犯罪以外の全体設定が増えたらここ。

# 5. `config/crimes.sk`

ここはかなり重要です。

**犯罪ごとの設定を一元管理するファイル。**

例えば概念的には、

```text
crime-id: flower

name:
    花踏み罪

jail-time:
    120

bail-item:
    copper ingot

bail-amount:
    3

bail-name:
    銅インゴット
```

という感じ。

そのため犯罪ファイル側では、

```skript
arrest_crime(player, "flower")
```

だけで済みます。

---

## この構造のメリット

例えば、

> 花踏み罪を30秒 → 2分にしたい

となった場合、

**`flower.sk`を変更する必要がありません。**

`config/crimes.sk`だけ変更。

```text
crime/flower.sk
       │
       │ 「flowerです」
       ↓
core/crime.sk
       │
       ↓
config/crimes.sk
       │
       ├─ 花踏み罪
       ├─ 2分
       ├─ 銅
       └─ 3個
```

という構造です。

これは今後のバランス調整にかなり便利です。

犯罪そのものではなく、

# 8. `core/crime.sk`

### 役割

**全犯罪共通の受付窓口。**

犯罪ファイルから、

```skript
arrest_crime(player, "flower")
```

のように呼ばれます。

処理の流れは、

```text
crime/flower.sk
       ↓
arrest_crime(player, "flower")
       ↓
ARREST GAME ON?
       ↓
対象ワールド?
       ↓
収監中ではない?
       ↓
犯罪が有効?
       ↓
config/crimes.sk
       ↓
罪状・刑期・保釈金取得
       ↓
arrest_create_jail()
```

です。

つまり、

> **すべての犯罪が最終的にここを通る**

のがポイント。

また、今後Survival限定にする場合も、ここで共通判定すれば全犯罪に適用できます。

**収監中のプレイヤー保護。**

```text
   ├── 脱走？
   ├── プレイヤー巻き込み？
   └── その他
```

という区切りにします。

特に、**「近くのプレイヤーやモブも逮捕時に巻き込む」みたいな面白い仕組みは、今のv0.0.04aには入れず、将来のゲーム要素として残す**のが良いです。

今はもう、システムを作り直す段階ではなく、**「これを実際に5～10人で遊んだらどうなるか」を見て、罪状・刑期・保釈金を調整する段階**に入っています。

* * *

そうですね。**ARREST GAMEは他のゲームより、ログアウト・サーバー再起動への影響は比較的小さい**です。

ただし、今の構造だと「完全に状態を復元する」わけではありません。

### プレイヤーがログアウトした場合

現在の仕組みでは、収監情報は変数に残っています。

```text
{arrest::player::UUID::jail}
```

なので、**ログアウトしただけなら「収監中」という状態自体は残ります**。

ただし、BossBarや刑期カウントについては注意が必要です。

* プレイヤーがログアウト
* 牢屋自体はワールドに残る
* 収監情報も残る
* 再ログインすると収監状態が残っている可能性がある
* ただし、その間の刑期をどう扱うかは現在の実装次第

という状態です。

### サーバーが落ちた場合

ここが一番重要です。

現在の牢屋情報はSkript変数なので、**サーバーが正常終了・再起動した場合にどこまで変数が保存されるか**という問題があります。

そして、仮に変数が残ったとしても、

```text
牢屋
  ↓
サーバー停止
  ↓
再起動
```

では、BossBarやタイマーの「実行中の処理」は当然止まります。

つまり、

> **サーバー停止中も刑期がリアルタイムで減り続ける、という保証はない**

です。

---

## でも、あなたの言う通り影響はかなり小さい

ここは重要で、ARREST GAMEは、

**「サーバー再起動＝ゲームそのものが壊れる」**

というタイプではありません。

例えばLineRaceみたいなゲームなら、

```text
ゲーム進行中
 ↓
サーバー停止
 ↓
タイマー・参加者・ゲーム状態
 ↓
途中状態の復元問題
```

が結構重要になります。

一方ARREST GAMEは、

```text
サーバー停止
 ↓
再起動
 ↓
/arrest on
 ↓
ARREST GAME再開
```

で基本的には復帰できます。

特に今は、

> **ARREST GAMEの対象ワールドを指定して、そのワールド内で犯罪を検知する**

というシンプルな構造なので、ゲーム全体の進行状態を複雑に復元する必要がありません。

---

## ただし「牢屋」は少し別

ここだけは今後考えてもいいところです。

例えばサーバーが落ちた瞬間、

```text

↓

↓

```

だったとします。

サーバー再起動後に、

```text
/arrest on
```

した場合、

**牢屋 #12をどう扱うか？**

という問題があります。

理想的には、

### パターンA：リセット型

```text
サーバー再起動
↓
/arrest on
↓
残っていた牢屋を無効化
↓
収監状態も解除
```

これが一番簡単。

### パターンB：復元型

```text
サーバー再起動
↓
/arrest on
↓
牢屋情報を確認
↓
残り時間を再計算
↓
BossBar再生成
↓
収監継続
```

これはちょっと複雑になります。

---

### 僕なら今はAでいいと思います

ARREST GAMEの性質を考えると、

> **サーバー再起動＝その時点の収監をリセット**

でいいと思います。

つまり、

```text
通常プレイ
   ↓
逮捕
   ↓
牢屋
   ↓
サーバー落ちる
   ↓
再起動
   ↓
/arrest on
   ↓
ARREST GAME再開
```

で、

**「前回の収監者を復元しない」**

というルール。

これなら非常にシンプルです。

しかもあなたが言うように、ARREST GAMEは**常時進行型のゲームではなく、犯罪が起きたときだけ動くゲーム**なので、この割り切りはかなり相性がいいです。

今の段階では、**ログアウト・サーバー落ち対策を大掛かりに作る必要はない**と思います。
むしろv0.0.04aでは、このまま遊んでみて、実際に「ログアウトしたら牢屋どうなる？」というケースが出てから決めるくらいで十分です。

```text
    │   ├─ CRIMES.md
    │   └─ JAIL.md
    │
    └─ skript/
        ├─ core.sk
        └─ jail.sk
```

という状態になります。

### 例えば

```bash
git add .
git commit -m "Release v0.2.10"
git tag v0.2.10
git push origin main
git push origin v0.2.10
```

この場合、`v0.2.10` をチェックアウトすれば、

```text
README.md
docs/ARCHITECTURE.md
docs/JAIL.md
skript/arrest/jail.sk
...
```

が**全部そのバージョン時点の状態**で取得できます。

---

### これが結構便利

例えば、

**v0.2.10**

```text
jail.sk v0.0.03
JAIL.md
```

だったものが、

**v0.3.00**

```text
jail.sk v0.1.00
JAIL.md
```

になった場合、

```text
v0.2.10 → その時点の仕様書
v0.3.00 → その時点の仕様書
```

として残ります。

なので、後から

> 「v0.2.10の牢屋ってどういう仕様だったっけ？」

となっても、**タグを見ればコードとドキュメントをセットで復元できる**。

## ただし1点だけ

GitHubの**Releaseページに添付するファイル**とは別物です。

```text
Git Repository
│
├─ README.md
├─ docs/
└─ skript/
```

これはGitの管理対象。

一方、

```text
GitHub Releases
└─ v0.2.10
    ├─ Source code (zip)
    └─ Source code (tar.gz)
```

はGitHubがタグから自動生成するものです。

だから個人的にはARREST GAMEなら、

**「MDもコードも全部Gitで管理 → バージョンごとにタグを打つ」**

で十分だと思います。

そしてREADMEには現在の最新状態を書き、**過去バージョンの詳細は各タグから確認できる**ようにするのが綺麗です。

* * *

はい。GitHubで日本語版・英語版を用意するなら、**一番一般的で管理しやすいのは「READMEは言語ごとに分け、詳細docsも必要なら言語別にする」方式**です。

ARREST GAMEなら、個人的には次の形がおすすめです。

## GitHubではREADME.mdを英語にするのが無難

例えば `README.md` を英語版にして、

```md
# ARREST GAME

A Minecraft arrest game built with Paper and Skript.

[日本語版 README](README.ja.md)
```

そして、

```md
# ARREST GAME

Paper + Skriptで作成するMinecraft逮捕ゲーム。

[English README](README.md)
```

とします。

これならGitHubを開いた人には英語READMEが表示され、日本語ユーザーはリンクから日本語版へ行けます。

逆に、**日本語をメインにしたいならREADME.mdを日本語、README.en.mdを英語**でも全く問題ありません。

## さらに良い方法：言語をディレクトリで分ける

規模が大きくなったら、

```text
docs/
├─ ja/
│  ├─ ARCHITECTURE.md
│  ├─ SPECIFICATION.md
│  └─ JAIL.md
│
└─ en/
   ├─ ARCHITECTURE.md
   ├─ SPECIFICATION.md
   └─ JAIL.md
```

にします。

この方式のメリットは、

> 「この仕様書は日本語なのか英語なのか」

が一目で分かること。

また、GitHub上で、

```text
docs/ja/JAIL.md
docs/en/JAIL.md
```

と対応関係が明確になります。

### そしてコード自体は日英共通

ここは重要です。

```text
skript/
└─ arrest/
   ├─ core.sk
   ├─ jail.sk
   ├─ bossbar.sk
   └─ crime/
```

は1つだけ。

言語によってコードを分けません。

ゲーム内表示だけ、

```text
messages/
├─ ja.sk
└─ en.sk
```

などに切り離せば、

```text
コード
  ↓
メッセージキー
  ↓
日本語 / 英語
```

という構造にできます。

これは今考えている**「ARREST GAMEのTitle・Chat・BossBar等を将来的に日本語/英語切替」**とも非常に相性がいいです。

個人的には、今の段階なら **READMEだけ日英 → ゲーム内メッセージを言語分離 → 仕様書は必要になったものから日英化** が一番きれいです。
