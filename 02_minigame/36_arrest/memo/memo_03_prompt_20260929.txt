【開発環境】
- Minecraft 26.2
- Paper 26.2-112
- Java 25
- Skript 2.16.1
- SkBee 3.25.1
- macOS
- 基本的にSkript中心
- まず小さなミニテストを作り、動作確認してから本体へ統合する
- コードはコピペしてそのままテストできる完成形で提示する
- 変更時はバージョン番号を上げる

============================================================
■ ARREST GAME 現在の目的
============================================================

プレイヤーがゲーム内で犯罪条件を満たした場合、

「犯罪検知」
↓
「逮捕」
↓
「牢屋生成」
↓
「一定時間収監」
↓
「看板へ指定アイテムを納品」
↓
「牢屋解除」

という仕組みを作る。

最終的には、

・犯罪ごとに逮捕条件を設定
・犯罪ごとに収監時間を設定
・犯罪ごとに納品アイテムを設定
・必要個数を設定
・複数人を同時に逮捕
・各牢屋を1、2、3……とID管理
・牢屋とプレイヤーを紐づける
・看板と牢屋を紐づける

ところまで作る。


============================================================
■ 現在テストしている犯罪
============================================================

まずは以下だけ。

1. 草を刈る
2. 30秒間その場から動かない

現在は「草を刈る」を実際の逮捕につなげている。

対象：

- tall grass


============================================================
■ 草刈り犯罪の現在仕様
============================================================

草を刈ると、

タイトル：
「草刈り無免許罪」

を表示。

逮捕されたプレイヤーの位置を基準に
その場へ牢屋を生成する。

牢屋生成後、
10秒間収監する。

10秒間はBossBarを表示。

10秒経過すると牢屋を削除する。

現在のテストでは、まずこの基本動作を確認している。

============================================================
■ 牢屋生成位置の基本ルール
============================================================

ARREST GAMEでは、基本的にすべての牢屋を
「逮捕されたプレイヤーの位置」を基準に生成する。

犯罪の種類によって基準位置を変えない。

例えば、

・草を刈った
・花を踏んだ
・30秒間動かなかった
・その他の犯罪

どの場合でも、

「逮捕された瞬間のプレイヤー位置」

を牢屋生成位置として使用する。

犯罪が発生したブロックそのものを
牢屋の基準にはしない。


Minecraft上では、

プレイヤー座標 Y
↓
プレイヤーが実際に立っているブロック = Y - 1
↓
そのブロックを牢屋の土台にする
↓
プレイヤーは土台 + 1

とする。

つまり、

土台 = プレイヤーが立っているブロック
プレイヤー = 土台の1ブロック上

とする。


例：

プレイヤー座標 Y = 65

土台 = Y 64
プレイヤー = Y 65
鉄格子 = Y 65～67
天井 = Y 68


重要：

「プレイヤーの位置」を牢屋生成の基本基準とする。

犯罪ごとに、

・犯罪が発生したブロック
・クリックしたブロック
・壊したブロック

などを牢屋の基準位置にしない。

最終的には、
「逮捕したプレイヤーの現在位置」
を共通の牢屋生成処理へ渡す。


============================================================
■ 牢屋の破壊防止
============================================================

牢屋としてARREST GAMEが生成した、

・reinforced_deepslate の土台
・reinforced_deepslate の天井
・iron_bars の側面

は、収監中のプレイヤーが
通常のブロック破壊操作で壊せないようにする。

ただし、

通常のワールドに存在する
reinforced_deepslate や iron_bars

まで壊せなくしてはいけない。


重要：

単純に、

if event-block is reinforced deepslate
    cancel event

のような全体判定にはしない。


「ARREST GAMEが生成した牢屋」
だけを破壊禁止にする。


つまり、

ARREST GAMEが生成した牢屋
→ 破壊禁止

通常のreinforced_deepslate
→ 通常通り

通常のiron_bars
→ 通常通り


とする。


============================================================
■ 牢屋の破壊禁止管理
============================================================

現在は1人用テストなので、
現在生成している牢屋の位置・範囲を変数として保持する。

例えば、

牢屋のX1
牢屋のY1
牢屋のZ1
牢屋のX2
牢屋のY2
牢屋のZ2

などを保存する。


将来的に複数人対応した場合は、

jail ID
↓
牢屋の範囲
↓
その範囲内の牢屋ブロック

という形で管理する。


例えば、

ID 1
→ 牢屋範囲1
→ 破壊禁止

ID 2
→ 牢屋範囲2
→ 破壊禁止

ID 3
→ 牢屋範囲3
→ 破壊禁止


とする。


============================================================
■ 牢屋解除
============================================================

牢屋解除時には、

ARREST GAMEが生成した

・reinforced_deepslate の土台
・reinforced_deepslate の天井
・iron_bars の側面

をSkriptから削除する。


プレイヤーが壊すのではなく、

Skriptによる正式な牢屋解除

として削除する。


牢屋の外側にある通常の地形は、
できるだけ削除しない。


============================================================
■ 現在うまくいっていること
============================================================

牢屋生成自体は成功している。

牢屋を生成する際、

同じ場所へ2回生成し、
間に2 ticks程度のwaitを入れる方式

で安定している。

この方式は現在うまく動作しているため、
必要がなければ勝手に大きく変更しない。

■ 牢屋IDの考え方
============================================================

牢屋IDは「現在存在している牢屋の識別番号」として使用する。


例えば、

1人目を逮捕
→ ID 1

2人目を逮捕
→ ID 2

3人目を逮捕
→ ID 3


とする。


将来的にIDを再利用するか、
常に新しい番号を発行するかは、
複数人テストができた段階で決定する。


まずは単純に、

「次の番号を発行する」

方式で実装する。


============================================================
■ 牢屋破壊防止の重要ルール
============================================================

牢屋の破壊防止は、
ブロックの種類だけで判断しない。

以下のような全体判定は禁止：

reinforced_deepslateなら破壊禁止
iron_barsなら破壊禁止


これでは通常ワールドのブロックまで
破壊できなくなってしまう。


必ず、

「ARREST GAMEが生成した牢屋の範囲内か？」

を確認してから破壊をキャンセルする。


イメージ：

プレイヤーがブロックを壊す
↓
そのブロックがARREST GAMEの牢屋範囲内か？
↓
YES
↓
破壊キャンセル

NO
↓
通常通り


将来、複数人対応した場合は、

全牢屋IDを確認
↓
該当する牢屋範囲があるか確認
↓
その牢屋のブロックなら破壊禁止


とする。


============================================================
■ 牢屋解除時の重要ルール
============================================================

牢屋解除は、

・収監時間終了
・必要アイテム納品

などによってSkriptが実行する。


解除時はSkriptから牢屋の範囲を削除する。


プレイヤーが壊すことは禁止。


また、
牢屋の外側にある通常の地形を
できるだけ巻き込んで削除しない。


そのため、
牢屋の生成範囲・削除範囲を
変数として正確に保持する。
